## 2. Make managed actor operations the sole execution/config ordering mechanism

### 2.1 Durable prepared operations

Extend existing machinery rather than add a new transaction engine:

- `actor/prepared.rs::PreparedOperationTicket` remains the FIFO predecessor/config/turn reservation.
- `actor/idle.rs::ActorIdleGuard` remains the selected actor's idle/source reservation for history edits and approval. `manager::prepare_idle_subtree` currently checks descendant idleness only when acquiring that guard. Preserve this acquisition-time contract; it is not a held subtree reservation.
- Config-only prepared transactions must complete while the actor runner is executing a tool that awaits its own `set_model` or `set_mode`. They use the existing `prepared::drive`/task ownership and actor FIFO, without `ActorIdleGuard`, a `HistoryEditWork` queue round-trip or waiting for the active turn to end. Preserve the active turn's immutable admission while later admissions see the committed config. Callbacks must not enqueue work on that same occupied runner and await it.
- Generalize `actor/history_edit.rs::HistoryEditAction::Prepared`/`commit_prepared_held_cancellable` for actual history replacement or an approval's held config/turn commit. Optional replacement history distinguishes clear from keep. Both this runner-owned history path and the independently driven config-only path use the same host preparation/publication contract and `PreparedOperation::commit_locked` finalizer. Do not implement a second config reducer or an uncheckpointed self-config exception.
- Put shared host transaction contracts beside existing actor prepared/history-edit types. Use existing `AgentParams`, `EffectiveAgentConfig`, `ConfigCommit`, checkpoint types and callbacks. Do not depend on `AppSession` or ratatui from the actor. Do not add a global transaction manager, a second operation counter or root/child transaction classes.

The contract is explicit:

1. Reserve the actor operation and obtain its FIFO predecessor. Resolve provider/model/mode/cwd and immutable admission inputs against that predecessor, never against later focus/current config.
2. For a durable mutation, prepare the exact public option candidate and reserve its base revision before async work. Add a small RAII revision reservation to `SessionOptions` only to prevent candidate commits from becoming stale during publication. It replaces conflicting coordinator lease/deferred state. It holds no mutex across awaits. `set_option_if_version` checks its version when acquiring this reservation. Conflicting public/plugin commits return the existing busy/stale error without holding an actor operation or another participant reservation while waiting; no mixed catalog generations are exposed.
3. Canonicalize and prepare reversible host provider/cwd effects. Any fallible host settlement belongs before durable publication. If preparation, adoption or checkpointing fails before publication, restore the previous host effects, abort the option candidate and leave actor config/history unchanged. Preserve explicit compound rollback-failed diagnostics; if rollback itself fails, mark the session unusable for new work and require reconciliation/shutdown rather than report a successful rollback.
4. Stage the candidate checkpoint outside actor/coordinator/writer mutexes. Thread the existing `CheckpointPublication` into the actual durable publish point. The writer checks session lock guard, runtime/incarnation and a captured authority-aware publication claim immediately before replacement. The claim validates invocation/task liveness, deadline, plugin owner/generation and captured manager/branch/host authority, then performs the request token's `try_publish()` CAS at that same boundary. An ordinary checkpoint followed by `finish_commit()` is insufficient if the checkpoint has already published irreversibly.
5. Cancellation, timeout, close, lock loss, invocation expiry or plugin revocation before the authorized publication claim cancels the same token. For already-popped work, actor processing/close must retain access to it. A canceled or revoked stage cannot later replace the file. Once an authorized claim wins, later invalidation cannot suppress finalization. The existing point-in-time `ModelMutationValidator` is insufficient by itself; implement the synchronized claim described below.
6. The actor-owned task owns publication and finalization independently of the caller future: the existing prepared-operation driver for config-only commits, or the runner for history/held-approval commits. Transfer the ready operation and reserved option revision to that task before publication. A preclaim caller drop cancels the request token; it must not destroy an already claimed operation. Close/cancel cancels that token before claim, but keeps claimed work owned until its actual storage result and synchronous finalizer complete. On successful publication, commit actor config/history and the reserved option revision infallibly using captured identity/version capabilities, even if close/caller drop occurred. Do not use the current `prepared::drive` late `lifecycle != Open` return for claimed work or rerun stale/liveness rejection after publication. Later close cancels/terminalizes a committed implementation turn, without retracting published config/history. A storage replacement failure remains a failure even if cancellation lost the claim; rollback reversible host effects and abort the candidate.
7. Publish the matching committed host/session snapshot and config notification, then acknowledge success/release any held turn. No async filesystem or provider operation runs under the actor state lock. A requesting future dropped during publication cannot strand reservations or suppress finalization.

Authority claim implementation belongs at the existing Lua authority and checkpoint boundaries, not in storage as a Lua dependency. Replace check-then-publish use of `LuaCtx::host_model_validator` with a captured synchronous claim callback that receives `CheckpointPublication` and performs validation plus CAS together. Add a short publication/revocation gate to the existing `PluginAuthority`; `revoke_plugin` invalidates its owner under that gate, then releases it before closing agents or running cleanup. Use the existing `TaskCell` mutex for scope/origin/deadline changes. Cancellation and manager/host retirement that can invalidate a captured claim must cancel its registered request token synchronously at the invalidating transition, not via a later async watcher. Register a request against those existing lifetimes while their current identity/liveness is validated; deregister on completion/abort. Use a synchronous cancellation registration tied to the existing token/lifetime, with registration and invalidation serialized under its short state guard. Do not use an async cancellation watcher or independent atomic read followed by a later CAS. Non-plugin work needs only its task/host/request capabilities.

Keep claim lock order explicit: existing writer pending/incarnation guard, then plugin authority gate, then task scope/cancellation claim guard, then the request CAS. Claim code must not acquire actor/graph/catalog locks or call a host adopter, Lua function or arbitrary validator while those locks are held. Manager/branch/host checks are captured capabilities whose invalidating transitions synchronously cancel the request; do their normal entry/preparation validation outside the writer lock. Invalidation paths use their own gate and cancel the token without acquiring the writer guard, and release authority gates before graph/agent cleanup. Reuse current lifetime/cancellation ownership rather than introduce an ancestry or option registry. Stage I/O happens before claim and final file replacement after these short guards are released, within the existing session-lock publication operation.

Retarget `revoked_model_preparation_does_not_install_or_checkpoint` and `revoked_checkpoint_restores_persisted_and_runtime_selection` (rename the latter to describe claim ordering), plus `captured_host_model_validator_rejects_revoked_plugin_and_expired_task` and `tool_host_model_validator_binds_live_plugin_authority`, with deterministic preclaim/postclaim gates. Assert actor config, public options, installed host state and reloaded durable state together: invalidation before claim rejects and rolls back; invalidation after claim cannot suppress successful finalization. Test plugin revocation and invocation cancellation through the real claim callback, not just an isolated validator.

Retarget existing tests `cancellable_prepared_commit_observes_publication`, `cancellable_prepared_commit_releases_reservation`, `cancellable_prepared_commit_does_not_need_runner`, `prepared_checkpoint_failure_preserves_config_and_history`, and `prepared_checkpoint_survives_cancel_and_close` to the shared contract. Extend the publication test with close/caller-drop before and after the publication claim instead of adding a separate suite. Retarget existing model/directory rollback and catalog transaction tests to the adapter and revision reservation. Retain `maki-lua/tests/agent_handles.rs::tool_spawn_preserves_executing_turn_configuration_after_committed_change` and `tool_ctx_reads_the_admitted_model_after_the_agent_commits_a_change`; bind a real gated durable adapter to their existing managed fixture. Assert the tool's self-awaited model/mode commit completes before its turn ends, matching actor/options/host/checkpoint state, while ctx and child inheritance still use the original immutable admission. No test may rely on an uncheckpointed self-config shortcut.

### 2.2 Source snapshots and terminal persistence

Expose a typed source snapshot from `ActorIdleGuard`. It captures target `AgentId`, actor identity/config generation, immutable history and predecessor cwd. Freeze selected-actor config/history edits while approval reads/prepares the plan, using the actor's existing idle/prepared reservation. Do not copy `IdleSessionLease`, its channel loop or its source-reservation counter into the actor.

`prepare_idle_subtree` rejects busy descendants at acquisition only. Retained idle children may accept/start work or create descendants after that check; no held manager subtree reservation is added. Their config/history remain independent of the target source snapshot. Pending child results may be accepted for the target, but `delivery::schedule` must not materialize a continuation while `state.idle` is held. Buffer them using the existing delivery bounds and withdrawal rules, without appending to the frozen target history. After successful clear, consume them at the approved turn's safe request boundary or a later continuation against the new context; after abort, resume against the unchanged context. Do not discard an undelivered result as obsolete transcript data. Existing explicit target admissions stay queued behind the held approval. Release the source guard on abort/caller drop, or transfer it to the actor-owned commit until UI projection permits the approved turn. Extend `idle_guard_allows_idle_live_child` and the existing pinned-approval fixture with a child admitted after source acquisition, a gated child result, and abort/drop rows. Assert that the child completes, target history remains frozen before publication, delivery resumes exactly once after release, and no reservation remains.

Ordinary turns need immutable admissions and terminal finalization, not a session lease held for the whole run. Keep the existing per-admission policy snapshot while config commits proceed at legal boundaries. Move successful-history persistence into the actor/backend settlement callback, using the live actor history for in-flight views and an acknowledged committed snapshot for durable session reads. Do not substitute the coordinator's old committed history for live checkpoint/Btw reads.

Order config-only and terminal-history persistence through the existing serialized host checkpoint writer and versioned merge, not by waiting for the turn runner. Config writes carry the candidate config/options plus the latest acknowledged history; they do not commit an in-progress tool transcript or restore the previous full session on rollback. Terminal writes carry their exact history epoch/revision and merge against the writer's latest committed config/options, so a terminal checkpoint captured earlier cannot revert a self-config commit. The writer promotes a published config candidate into its existing latest/provisional state before acknowledging it; pending terminal/TUI saves rebase on that state. A config-only driver never waits for terminal settlement of its own turn. A settlement callback may await an earlier in-flight config publication/ack without holding actor/option/writer mutexes, but that publication cannot call back into settlement. Retarget `pending_history_then_config_keeps_truthful_history_ack`, `in_flight_history_retry_handles_config_advancement` and `committed_config_survives_failure_and_retries_with_lease_history` (rename after lease removal) to prove both completion orders and preserve history acknowledgements across config failure/retry.

ACP transport `PendingOperation` continues to hold its request until terminal response; it is not an execution lease. Isolated operations capture the source/settings they need without holding primary-history ownership. Idle/manual compaction uses the same actor history transaction and retains persistence-before-success/rollback behavior. Keep config changes, history edits, admissions and subtree idleness in one actor ordering model.

Public option reads/subscriptions derive built-ins from the corresponding committed actor config and reserved option version. Historical events/turns retain their captured config generation rather than reread newest config. Retain committed checkpoint information only where required for durable reads and recovery; do not retain duplicate writable live state.

Plugin option replacement is a catalog-wide batch, not an independent actor config publication for each session. Preserve `SessionOptionCatalog::replace_plugin_options_with_validator`, its per-session prepare/checkpoint/Commit-or-Abort rendezvous, live participant generation reconciliation, `SessionOptions::commit_batch` and version-conditional batch restore. These are catalog responsibilities, not an execution scheduler. Each participant holds the same RAII option revision reservation used by actor-bound/public mutations while awaiting the catalog decision; actor config preparation acquires it before any reversible host effects. Acquire participant reservations in the existing deterministic `(session_id, generation)` order with nonblocking busy/stale rejection, never while holding an actor FIFO head waiting for another participant. On conflict, abort/release all prepared participants before returning the existing busy error. Async validators cannot await a conflicting config mutation while retaining the reservation; such mutation returns busy rather than deadlocking.

Prepare and checkpoint each participant's option candidate without changing its public snapshot. Only after all prepare/validation succeeds, recheck that the staged session IDs/generations exactly match the catalog's live set, reconcile changed participants as today, then perform one reserved `commit_batch` and catalog definition/revision swap under the catalog boundary. Release locks before decision replies or async work. Preserve lock order `DIRECTORY -> CatalogState -> SessionOptions` in sorted participant order where those locks are nested; actor/writer locks are not held across catalog work. Do not apply section 2.1's per-actor publish-then-public-finalize rule separately to these catalog participants.

Abort, failed prepare, dropped caller/decision channel or predecision close restores every participant's previous checkpoint and releases its reservation through the existing participant-owned decision cleanup. Keep this cleanup owned independently of the caller. Once the batch decision succeeds, participants complete/release even if the caller drops. If a participant closes or its Commit acknowledgement fails, retain the existing `restore_batch_if_versions` and previous-definition rollback, refusing to overwrite a newer option update; keep reservations through that decision/rollback. Preserve the current limits: public catalog options commit as a batch, but checkpoints across separate session files are not crash-atomic. Do not add a distributed transaction log. Rollback write failure is explicit and marks the affected session unusable instead of reporting consistency.

Adapt `plugin_replacement_rejects_active_lease_without_partial_commit` to an active conflicting actor/option reservation, retain `plugin_prepare_checkpoint_failure_exposes_no_mixed_generation`, `prepared_session_reconciles_plugin_replacement_before_activation` and `replacement_reprepares_session_activated_during_validator`. Extend the existing two-session busy/failure test with a concurrent actor-bound config mutation and caller-drop/close-before-decision rows. Assert no partial public generation, checkpoint rollback, eventual reservation release and subsequent successful mutation. Retain `rollback_does_not_overwrite_a_newer_option_update` and `duplicate_restore_target_is_rejected` as the batch rollback checks.

# Risks, Blockers, and Required Decisions

The operator requested all approved cuts and upward deep consolidation, then required "Commit at each major change" at handoff. Task-scoped autocommits are authorized under section 1.5; pushing and history rewriting are not. This authorizes root clear-context becoming an in-place clear: it preserves identity, children, options/mailbox/draft and cumulative accounting; it does not create an independently resumable planning session. `/new` remains the explicit new-session workflow. The approval UI wording and corresponding tests change accordingly. No separate transcript-fork feature is included.

Resolved design constraints:

- Parent identity is already manager-owned. A target always has a concrete AgentId; a missing target never means root. Do not follow earlier audit suggestions to represent a root approval target as None or duplicate parent IDs in every new work structure.
- Shared execution does not require identical host effects. Storage destination, fixed print mutation policy, user questions/rendering and wire completion timing are appropriate adapter distinctions. They must not create separate schedulers or weaker security checks.
- Ordinary coordinator history replacement cannot be called from a held source lease and cannot provide cancellation-safe root approval. The new actor-owned publication path replaces that entire interaction, avoiding a lease deadlock and a second checkpoint.
- The before/after-publication cancellation/authority contract and reserved option revision prevent stale durable writes or disk/runtime divergence. Their state replaces coordinator lease/deferred machinery. Config-only work uses the existing detached prepared driver so self-awaited mutations cannot deadlock the occupied turn runner. Actual history edits retain idle runner ownership; these are two execution requirements under one FIFO/commit contract, not two schedulers.
- The headless migration must be complete before unmanaged Lua fallback deletion. Leaving only TUI managed would break frontend tasks and is not an acceptable partial result.
- Typed presentation IDs preserve notification/recovery/cancel fencing. TurnId alone is insufficient for control/compact or grouped presentation; retaining frontend presentation state is intentional.
- Subtree idleness is an acquisition check, not a held lock over descendants. Approval freezes the selected actor; later child work stays permitted and its delivery waits behind that actor's history transaction. This preserves the existing concurrency contract without adding manager admission state.
- Production frontend nested-task tests need the small PluginHost/provider-script fixture extensions listed in Test Strategy. Include that work and its named AC.1/AC.8 scenarios before removing unmanaged coverage. There is no accepted untested frontend migration.
- The approved delivery metadata removal does not remove full retained-result provenance or authority checks. An audit delegate initially recommended moving the cache; that recommendation was rejected because it contradicts the approved shrink.

Scope is a cross-crate refactor, not a promise of a particular line reduction. Audit counts for coordinator/approval were gross deletion boundaries with replacement costs unknown. Measure the complete result and reject convenience abstractions/duplicate tests that increase size without removing the corresponding old path. If a materially new product behavior or a substantially larger infrastructure project becomes necessary, stop and present the specific decision; do not silently drop features, weaken authority, or keep dual architectures.
