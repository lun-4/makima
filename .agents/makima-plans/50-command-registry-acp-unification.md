## Goal

Make ACP a faithful Maki command frontend: advertise every command that is usable outside the TUI, dispatch advertised commands through the normal command registry, and exclude only explicitly TUI-only commands. Require Lua command authors to declare whether each command is TUI-only.

## Implementation Summary

Replace ACP's current blanket builtin registration plus `UnsupportedFrontend` stubs with an ACP-specific command runtime that shares the command registry's metadata, precedence, custom commands, Lua commands, and MCP prompts while implementing the portable builtin behaviors. Add mandatory `tui_only` metadata to Lua command registrations and carry it through registry projections so ACP can filter its advertised command list without inspecting producer IDs. Mark commands whose semantics require interactive TUI state or widgets, including tasks, queue, and sessions, as TUI-only; retain normal dispatch for portable builtins and all explicitly non-TUI Lua commands.

Relevant touch points are the existing `maki-commands` workspace crate at `maki-commands/src/lib.rs` for the shared command registry, builtin descriptors, and registration metadata, `maki-agent/src/command.rs` for custom-command metadata and registration, `maki-lua/src/api/tool.rs` and `maki-lua/src/api/util/command.rs` for Lua declarations and runtime metadata, `maki-ui/src/components/command.rs` and `maki-ui/src/app/mod.rs`, `maki-acp/src/server.rs` (including its current command routing, session prompt handling, and advertisement helpers), bundled registrations under `plugins/` (`sessions`, `thinking`, `splashes`, `perf`, `mode_plan_override`, `memory`, and `bash`), plus generated/user-facing command and ACP documentation. This is intentionally breaking for Lua command declarations and ACP's previous unsupported-builtin behavior.

## Implementation Plan

1. Extend command metadata and Lua registration.
   - Add a required boolean `tui_only` field to `maki.api.register_command`; reject missing or non-boolean values with a clear registration error.
   - Store the value in Lua's `CommandEntry` and in the command registration metadata produced by `maki-lua`/`maki-agent`, so it survives plugin publication and registry snapshots.
   - Update every in-repository Lua command registration and all Rust `CustomCommand`/registration fixtures to specify the new policy explicitly. Classify every current bundled Lua registration explicitly: `/sessions` and `/rename` (`plugins/sessions/init.lua`), `/splash-fps` (`plugins/perf/init.lua`), `/automode` (`plugins/bash/init.lua`), `/splash` (`plugins/splashes/init.lua`), `/memory` (`plugins/memory/init.lua`), `/thinking` (`plugins/thinking/init.lua`), and `/plan` plus `/build` (`plugins/mode_plan_override/init.lua`). Mark `/sessions`, `/rename`, `/splash`, `/splash-fps`, and `/memory` TUI-only; mark `/automode`, `/plan`, and `/build` non-TUI; mark `/thinking` TUI-only because its handler opens a selector. Classify bundled registrations explicitly: `/sessions`, `/rename`, `/splash`, `/splash-fps`, and `/memory` are `tui_only = true` because they use TUI pickers, overlays, modals, or UI feedback; `/automode` is `tui_only = false` because it mutates agent configu[line truncated]
   - Extend command documentation and Lua API examples to explain that `tui_only = true` excludes a command from non-TUI frontends and that the field is mandatory.

2. Give registry registrations an explicit frontend-availability projection.
   - Add a required `tui_only: bool` field directly to `CommandSpec`; all registration constructors must set it explicitly. Builtin registrations set the fixed builtin policy, Markdown registrations set `false`, and Lua registrations copy the declared value. Expose it through `ResolvedCommand::spec()` and `RegistrySnapshot` so the ACP projection and dispatch-time availability guard inspect the winning registration after precedence resolution. The registry remains owned by the existing `maki-commands` crate; `maki-agent` continues adapting Markdown/Lua/MCP sources into its registrations, and `maki-acp` consumes the registry through its existing `CommandDispatcher` integration from this PR.
   - Preserve command argument hints end to end: add the parsed Markdown frontmatter argument hint to `CustomCommand`, add an explicit optional Lua `argument_hint` string field to `register_command` (omitted means no hint; non-string values are rejected), store it in `CommandEntry`, and copy both into `CommandDocs.argument_hint`. For MCP prompts, derive the hint from ordered prompt arguments: zero arguments means `None`, one required argument is `<name>`, optional arguments are `[<name>]`, and multiple arguments join those forms with spaces. ACP advertisements must expose these hints without changing command arity validation.
   - Centralize the repeated builtin metadata conversion and define the builtin availability policy in one place. Use this explicit policy for the current builtin set: ACP-available are `/compact`, `/new`, `/model`, `/cd`, `/btw`, `/yolo`, `/fast`, and `/workflow`; `/thinking` is TUI-only at both layers: the builtin descriptor is marked TUI-only, and the bundled Lua registration is also marked TUI-only because its handler opens a selector; the resolved winner is determined by the existing producer precedence and must be asserted, rather than assuming the Lua registration overrides the builtin; TUI-only are `/tasks`, `/help`, `/usage`, `/queue`, `/theme`, `/mcp`, `/login`, `/exit`, and `/reload` because their normal behavior is a picker, modal, queue/session UI, or process/UI lifecycle operation. Treat bundled Lua `/sessions` as TUI-only through its explicit Lua declaration. This is a frontend-semantics classification, not a builtin/custom distinction.
   - Preserve command precedence and collision behavior. A TUI-only builtin must not prevent an explicitly higher-priority portable registration from winning if the registry rules already allow that override.

3. Refactor the TUI runtime to consume the shared metadata while preserving behavior.
   - Continue registering the full builtin set in the TUI, including TUI-only commands, and route them to the existing `BuiltinRoute`/`App::execute_builtin_route` implementations.
   - Update builtin registration construction to use the centralized metadata/policy and keep model/theme completions and all existing TUI behavior unchanged.
   - Update TUI tests and fixtures for the new metadata, including the invariant that every builtin has a route and that TUI-only commands remain available in the TUI.

4. Replace ACP's unsupported-builtin shim with a real ACP command runtime.
   - Refactor the existing ACP command routing and registration directly in `maki-acp/src/server.rs` rather than creating a second registry or targeting a nonexistent adapter module: remove its dependency on `BUILTIN_COMMANDS` as a list of commands to register and remove `BuiltinRoute::Unsupported` plus the producer-ID filtering workaround.
   - Register the portable builtins with actual ACP routes/behaviors, alongside custom Markdown commands, non-TUI Lua commands, and MCP prompts. Preserve invocation target/lifecycle correlation and the deterministic agent-turn classification fixed in the current PR.
   - Implement ACP-side handling for portable builtins whose normal semantics are meaningful without a TUI, such as model selection, compaction, working-directory/configuration toggles, and agent-turn-producing commands, using the existing session/agent channels and ACP responses/updates. Do not emulate TUI widgets for commands classified TUI-only.
   - Ensure commands that end locally complete the invocation and return an ACP prompt response; commands that produce an agent turn submit the rendered prompt and let the agent lifecycle complete the request; validation and session-closed failures transition the invocation to `Failed`.
   - Keep custom commands and MCP prompts on the normal registry dispatch path rather than parsing or expanding them in ACP-specific code.

5. Make ACP advertisement match dispatchability.
   - Filter `RegistrySnapshot` entries by the new TUI-only metadata, not by builtin producer identity, when building `available_commands`.
   - Advertise all ACP-available winning commands, including portable builtins, custom commands, non-TUI Lua commands, and MCP prompts, with their descriptions and argument hints.
   - Continue publishing updates when registry generations change after plugin reloads or MCP reconnects.
   - Preserve unknown slash-prefixed text as an ordinary prompt. Add an explicit ACP dispatch-time availability guard: resolve the candidate, inspect its winning `CommandSpec::tui_only`, and when it is TUI-only skip command dispatch and forward the original prompt unchanged as an ordinary agent prompt, exactly like an unknown slash-prefixed input. This is literal forwarding, not an ACP error; the command is omitted from advertisement and never returns `UnsupportedFrontend`. Keep TUI-only registrations in the shared registry for TUI, but never route them through ACP behaviors or return `UnsupportedFrontend`.
   - Extend ACP's routed agent-turn variants to carry the original `Vec<ImageSource>` alongside rendered text, pass it into `agent_input`, and preserve MCP prompt metadata. Text resources and resource links remain part of the extracted text using the existing conversion. Any unsupported/custom ACP content block produces the fixed invalid-params error `unsupported content block in command prompt`; local commands with images or any other non-text content produce the fixed invalid-params error `local commands cannot include non-text content`. These are unconditional behaviors, not fallback options. This replaces the current blanket “known slash commands cannot include images” restriction and matches ACP's allowance for commands alongside other prompt content.

6. Update tests and documentation.
   - Add Lua API tests for mandatory `tui_only`, storage/publication of the flag, and rejection of missing/invalid values.
   - Add registry/projection tests proving TUI-only commands are retained for TUI, omitted from ACP, and do not require producer-ID filtering.
   - Add ACP tests for advertisement of all portable builtins and non-TUI plugin commands, omission of `/tasks`, `/queue`, `/sessions` and other selected TUI-only commands, dynamic projection updates, and dispatch of each portable builtin category. Use an exhaustive bundled-registration fixture/assertion: the current non-TUI set is exactly `/automode`, `/plan`, and `/build`, while `/sessions`, `/rename`, `/splash-fps`, `/splash`, `/memory`, and `/thinking` are all omitted; the test must compare the complete published projection against these sets so a newly registered non-TUI command cannot be silently omitted. Add an explicit registry integration test that constructs the actual bundled Lua registrations and verifies winner resolution, especially the builtin-versus-plugin `/thinking` collision.
   - Replace the existing test that expects `/help` to return `UnsupportedFrontend`; assert the intended behavior for a TUI-only command instead. Retain tests for custom command expansion, MCP prompt routing, stale targets, local completion, agent-turn acceptance, model validation, and unknown slash text.
   - Update `site/docs/content/acp/_index.md`, generated command/Lua API documentation inputs as appropriate, and `site/docs/content/commands/_index.md`/headless documentation so command availability and the `tui_only` contract are accurate. Do not document commands as ACP-available unless their ACP route is implemented.

## Risks, Blockers, and Required Decisions

- The builtin availability decision is fixed for this plan: ACP supports `/compact`, `/new`, `/model`, `/cd`, `/btw`, `/yolo`, `/fast`, and `/workflow`; `/thinking` is represented only by its bundled Lua registration and is TUI-only because the handler opens a selector; `/tasks`, `/help`, `/usage`, `/queue`, `/theme`, `/mcp`, `/login`, `/exit`, and `/reload` are TUI-only. `/sessions` is a bundled Lua registration, not a builtin descriptor, and is explicitly marked `tui_only = true`. If implementation discovers that one selected portable behavior cannot be represented without violating ACP semantics, stop and surface that specific decision rather than silently changing the advertised contract.
- Lua handlers can call UI APIs even when declared non-TUI. `tui_only` is an advertisement/availability contract for now, not function-level enforcement; runtime failures from a misdeclared handler remain possible and should be reported cleanly. Function-level capability restrictions are out of scope.
- At `maki-acp/src/server.rs::handle_prompt`/`extract_prompt_content`, ACP commands preserve images and convert text resources/resource links for agent-turn routes; local routes reject non-text blocks with the fixed documented error `local commands cannot include non-text content`, and unsupported/custom blocks reject with `unsupported content block in command prompt`. These are mandatory behaviors, not fallback options.
- Markdown custom commands have no new Lua declaration field. They are treated as portable because their normal behavior is prompt expansion, while UI-dependent behavior belongs in Lua and must declare `tui_only`.
- The breaking Lua API change is intentional and accepted. Existing plugin examples/tests and all bundled registrations must be updated in the same change.
