## Goal

Rebuild issue #123 on `plan-implementation-model-v2`, based on merged mistress, so plan approval can stage an implementation model and start either keep-context or fresh-context implementation with that model. Preserve the planning session on cancellation or preparation failure before approval commits, without provisional provider installation or rollback.

## Implementation Summary

The UI behaviour from `57e1867d` and `56609f16` on the preserved `plan-implementation-model` branch is ported by hand, not cherry-picked. The existing model picker, actor-owned configuration, FIFO operation queue, per-turn snapshots, runtime identity filtering, and write-behind persistence from #146 stay as they are. This design supersedes the old branch plan's provisional-adoption AC.6/AC.7.

The plan form stages an optional implementation model. Picking it in plan purpose only changes the form; it never switches the session model, installs a provider, or writes preferences or recents. A conditional `Use current model` row clears the override.

`maki-agent` gains one generic prepared operation in the actor FIFO: `reserve_prepared_operation(optional_turn)`, `resolve(change)`, `wait_ready()`, `commit()`. At the FIFO head it applies the change to the predecessor config without publishing it, runs admission preparation and async prompt readiness off the actor lock, and holds the head while Ready. Commit publishes config, Build mode, and the optional turn together. Dropping or cancelling the ticket before commit releases successors and publishes nothing. `ConfigChange::PatchAndMode` combines the model patch with the resolved Build mode.

Both approval paths need an idle planning runtime and idle managed descendants. Busy approval is rejected with a retry message, never queued. An idle guard holds new execution until the approved turn starts; starting that turn ends the reservation. The plan text is read once, off the UI thread, when the source is captured, and that exact text is what runs.

Keep-context approval commits the prepared turn on the planning actor. Fresh-context approval prepares the whole candidate runtime first: config, first admission, and the target session lock, with its runner start deferred so nothing runs before activation. It then swaps through the existing replacement transaction, retires the outgoing session like a reset, and releases the candidate runner. Any failure or cancellation before the swap keeps the original session, form, plan, and config. After commit, cancellation stays in Build mode with the selected model.

## Risks, Blockers, and Required Decisions

- Resolved operator decision: fresh runtime and first admission preparation complete before swapping; precommit failure/cancel retains the original planning session. After successful approval, execution cancellation/failure does not roll back model, Build mode, or the new runtime.
- Prepared runtimes currently contain running actor tasks. Deferred runner-start is required infrastructure, not optional mitigation. Its drop/close semantics must settle tickets even before runner activation.
- Provider construction can execute auth scripts and must not run on the UI thread. Already-started subprocess or detached prompt effects may finish after cancellation; results cannot commit or execute stale work.
- Source snapshot guards deliberately delay later actor-owned setters/admissions during fresh preparation. They must cancel promptly and never block already-active turn lease release. Successful heavy replacement discards queued outgoing work as current replacement does; failure releases it.
- Final runtime activation must contain no remaining provider/prompt/filesystem preparation. Failed activation must not install startup/provider projections or poison storage state. Extend production fixtures to test the full failure boundary.
- Ordinary admissions remain on existing APIs; avoid making every request use two-phase approval. The new primitive must remain generic, small, and free of plan-specific types in `maki-agent`.
- The form may move to guest plugins in PR8A. Keep plan UI state in `maki-ui` and generic configuration/admission mechanisms in `maki-agent`.
- No accepted test-infrastructure gaps or unresolved product decisions. Full state-log persistence/rewind and file restoration remain separate PR6 work.
