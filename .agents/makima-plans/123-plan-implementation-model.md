Preserve the planning session on cancellation or preparation failure before approval commits, without provisional provider installation or rollback.

### 2. Add one generic prepared actor operation

Current evidence: `ConfigChange::Patch` and `ConfigChange::Mode` are separate (`actor/config.rs`); `dispatch_mode_change_op` commits Mode and later creates a follow-up (`event_loop.rs:570-630`); ordinary admission is a separate FIFO entry. A config ticket followed by a turn is insufficient because a failed ticket would otherwise release an implementation admitted on the old settings.

Add a combined change such as `ConfigChange::PatchAndMode { patch: ConfigPatch, mode: AgentMode, mode_def: ModeDef }`. Reuse the existing patch reducer/capability normalization, then set the resolved mode. Do not duplicate model validation or read a mutable registry during execution. Existing Patch and Mode semantics remain unchanged.

Add one generic reservation operation to the existing actor FIFO, not a parallel scheduler. It supports an optional pending turn and a configuration change supplied after side-effect-free provider preparation. Proposed surface: `reserve_prepared_operation(optional_turn)` returns an owned reservation; `resolve(change)` supplies the prepared change; `prepare()` waits for a Ready token; `PreparedOperation::commit()` returns the committed full config and optional `TurnTicket`. A snapshot-only reservation with no change and no turn is used briefly for fresh-context source settings. Use descriptive final names consistent with existing tickets.

Reserve synchronously under actor state before starting provider work. At the FIFO head, apply the change to the preceding committed configuration without publishing it. Normalize the pending input from that candidate policy and resolved mode. Run existing synchronous admission preparation on the blocking pool outside actor locks. Finish asynchronous admission readiness before marking Ready. Store the exact candidate and snapshot in the same FIFO entry. Ready holds the head until explicit commit or abort; later setters/admissions cannot overtake it, while already active execution continues.

Commit under the state lock: verify identity, lifecycle, and Ready ownership; publish candidate configuration using the existing equality/no-op generation rule; materialize the optional turn using that exact configuration/generation/snapshot; remove the operation; drive successors. No externally supplied callback or blocking work runs under this lock. Observer publication remains nonblocking. Return the full commit even for a no-op generation, so UI completion need not wait for an observer event.

Cancellation, expiry, or dropping the sole reservation/prepared owner before commit removes the operation and releases successors without publishing the candidate. If a turn ticket was created, terminalize it exactly once; do not render a phantom implementation user message. Late preparation/readiness results must match operation identity and lifecycle before changing anything. After commit, cancellation stops the turn and does not restore Plan mode or the previous model.

Extend raw projections, counts, remove/remove-visible, clear, cancel-turn/correlation/existing, close/shutdown, queue-empty publication, and waiter settlement for the new operation. Snapshot-only operations are invisible and follow configuration-reservation cancellation semantics; turn-bearing reservations follow work cancellation semantics. Retain current control ordering and no-op batching behavior. Remove any unused wrappers introduced during development.

Add an optional backend admission-readiness hook with a default no-op implementation. Invoke it only for prepared operations so ordinary admissions retain current semantics. The TUI hook awaits the captured prompt-slot/MCP receiver without actor locks and reports closure/error before Ready. Replace the current prompt-slot producer's `recv_async().await.unwrap_or_default()` error erasure for prepared approval: preserve slot-request closure as an explicit error in the captured result. Ordinary admission may retain its existing empty-slot fallback through an explicit preparation policy; do not change that compatibility behavior silently. Test real inner slot-request closure separately from outer resolved-input receiver closure and MCP failure. Preserve the resolved result for execution without consuming it twice or cloning competing flume receivers. Prefer adding an explicit already-resolved value to the prompt-input representation if that is simpler than recreating a preloaded receiver; adapt `prepare_run` through one shared accessor. Keep the captured slot request, cwd, instructions, mode definition, MCP identity, and tool bindings unchanged.

Race provider preparation, blocking-preparation completion, and readiness waits against operation cancellation and the existing configured preparation timeout. Blocking callbacks may physically finish later but cannot materialize stale work. Detached Lua/MCP requests already dispatched need not be undone; document that cancellation releases the approval wait, not arbitrary external effects. Maintain current cancellation-aware execution setup for ordinary turns.

### 4. Keep-context approval

Replace eager implementation actions with a single approval intent carrying clear/keep choice and staged model. Capture the plan path/content and parallel setting at request time. Read plan files on the blocking pool; read failure is visible and preserves the form rather than becoming an empty plan through `unwrap_or_default`.

Resolved operator decision: both approval paths require an idle planning runtime and idle managed descendants. Reject busy approval with a visible retry message; do not queue approval, cancel planning work, or wait for it. Check manager activity, actor active/popped work, pending work before the reservation, coordinator lease/history finalization, and outstanding directory/history mutation. Add a narrow idle-only preparation guard integrated with existing actor/manager admission locks: acquire it only if those checks succeed, hold new execution and descendant starts while preparing, and reject or abort if concurrent work wins. Do not rely on App Status or a stale manager snapshot alone. Earlier queued work counts as busy; later ordinary work is retained behind the guard. Release it on abort, or transfer execution permission solely to the approved turn on commit. Existing managed-turn registration and coordinator lease mechanisms provide the synchronization; add deterministic races for guard acquisition versus root pop/child start. No general wait-for-quiescence framework is needed.

Keep one per-runtime pending approval owner with request identity and reservation ownership. Lock form submission/editing/model staging while pending; duplicate approval is ignored. Esc aborts the uncommitted owner and unlocks the existing form. Runtime replacement, mode exit, lock loss, and an obsolete plan lifecycle abort it. External model/options setters remain FIFO: predecessors are included, successors wait behind the reservation and run after commit/abort. Do not issue compatibility-slot mutations as approval preparation.

Resolve model policy/parsing/provider construction through the same side-effect-free preparation used by normal actor setters. With no override, reuse the predecessor actor provider/model and options; do not reconstruct a provider or copy stale App settings. With an override, patch only the model; predecessor thinking/fast values undergo normal capability normalization. Combine that patch and resolved Build definition with implementation admission in the prepared operation.

On Ready, validate request/runtime/form identity and plan-content fingerprint again. If changed, abort and retain the form with a visible retry message. The implementation input contains the exact captured plan text. A file edit after the last off-thread verification cannot change execution instructions; filesystem writes are not atomic with the UI commit. Commit the prepared operation. Project its returned full config immediately through the runtime's generation-aware helper. Update recents/preferences only after successful commit. Display the approved plan and implementation user message and clear the form/PlanState only then. Do not dispatch another SendMessage or mode-change follow-up: the actor already owns exactly one implementation turn.

Allocate the future root correlation/run ID in the pending intent without incrementing visible App.run_id, firing TurnStart, or changing the shared backend run ID. Put that exact correlation into the prepared turn. On Ready, process approval on the event-loop thread in one non-awaiting dispatch: commit actor operation; publish returned configuration and matching App/shared run ID; install user-message/status bookkeeping; fire TurnStart exactly once. Agent events may be enqueued immediately by the runner, but event draining must not occur between commit and these publications. If commit fails, publish none of them. Idle-only approval avoids rewriting an active turn's ID. For fresh approval, install all run-ID/display/status bookkeeping before releasing the candidate runner gate. Tests must deliver immediate first/terminal events through ordinary EventLoop draining and assert no filtering loss, duplicate TurnStart, or phantom aborted message.

Adapt UI run bookkeeping and cancellation correlation to the existing root/event-envelope conventions. Extract a method that performs only display/status bookkeeping for an already-admitted implementation; do not create a second queue or clone AgentInput to avoid ownership transfer. Test actual provider requests through normal internal-event delivery and tick.

### 5. Fresh-context approval with preparation before swap

Resolved operator decision: prepare the candidate runtime and first admission before swapping. All pre-approval preparation failures/cancellation preserve the original planning runtime, form, plan, history, and configuration. After approval commits, later execution failures/cancellation remain in the fresh Build session. Full rewind/restoration is deferred.

Use the same generic prepared-operation primitive with no turn/change as a source snapshot guard. Reserve it in the outgoing actor FIFO, await Ready, and hold its full config while preparing the candidate. Earlier settings changes are included; later actor-owned settings/admissions wait until the transaction commits or aborts. The outgoing actor never receives the selected implementation model or Build mode provisionally. On failure abort the guard, allowing queued setters/work to continue.

After the idle-only guard is acquired and coordinator lease/history finalization has completed, capture an immutable source snapshot: actor ConfigCommit, authoritative coordinator cwd, history revision/identity, permission state used for replacement, and absolute plan path/content fingerprint. Resolve relative plan paths against that captured cwd. Fresh candidate history is explicitly empty, apart from the approved plan display and implementation input; do not copy the source mirror. Hold a coordinator session lease during preparation to defer directory/history mutation, but race lease acquisition against cancellation/timeout and reject busy/pending mutations instead of waiting for active work. YOLO/plugin settings retain their existing ownership: capture them at the boundary and revalidate any values used for candidate permissions at final commit. Release the lease/guard on all paths. Compare source cwd, history revision, plan fingerprint, runtime and lock identity immediately before activation; abort on change. This avoids treating the actor-config FIFO as a cwd/history guard.

Use captured settings/provider/model plus the staged override, capability normalization, cwd and existing replacement permission semantics to construct the candidate runtime. Never derive the selected model from the global startup slot. Move provider construction and plan/instruction filesystem work off the UI thread. Prepare UI/runtime objects on their required thread; do not move thread-affine App/Lua state through the blocking pool. Keep completion processing nonblocking and identity-filtered.

PreparedAgentHandles currently wraps a live actor runner, not an inert runtime (`agent/mod.rs:254-289,617-681`). Add a narrow deferred runner-start/activation boundary for private prepared replacement actors. Their configuration/admission preparation driver may run, but their runner must not consume queue work or publish provider requests before activation. Ordinary runtime construction remains unchanged. Dropping a deferred candidate shuts down its actor and settles tickets without waiting forever for a runner that never started. Reuse manager/actor construction rather than inventing a second executor.

Seed the candidate actor with the selected full Build configuration. Prepare its first implementation through a turn-bearing prepared operation, including asynchronous readiness. After Ready, commit that operation privately while runner start is still deferred. Its config belongs only to the candidate runtime and no execution is possible. Carry the candidate and already-prepared/admitted implementation as one owned transaction. Abort/shut down the candidate on any failure before swap.

At final completion, revalidate outgoing runtime/request/plan identity and lock ownership. Claim the target session lock and activate the candidate coordinator/mailbox/command target using the existing replacement failure path. No provider setup or prompt resolution remains at this boundary. Swap only after fallible activation succeeds. Transfer lock ownership, seed/bind storage and install compatibility projections only in the successful activation transaction; failures must not overwrite outgoing runtime state or leave a candidate session snapshot/file behind. Install approved plan/user display, App/shared run-ID state, streaming bookkeeping, and exactly one TurnStart before releasing runner start. Verify the outgoing manager subtree remains idle under the held guard; shut down/retire it without overlapping active tools, using existing lifecycle cleanup, then release the candidate runner. No agent-event draining occurs inside this non-awaiting final publication sequence. Release the source snapshot guard on every path. Preserve existing heavy-transition policy: outgoing queued work is discarded on successful replacement; on failure it remains eligible after abort. Do not add stable queue IDs or broad queue preservation.

The only execution after swap is the already-admitted implementation. Remove the old replacement post-commit SendMessage for this flow. Retain normal NewSession/resume/rewind behavior and tests. Do not add parent links or state-log fields in this PR.

## Risks, Blockers, and Required Decisions

- Resolved operator decision: fresh runtime and first admission preparation complete before swapping; precommit failure/cancel retains the original planning session. After successful approval, execution cancellation/failure does not roll back model, Build mode, or the new runtime.
- Prepared runtimes currently contain running actor tasks. Deferred runner-start is required infrastructure, not optional mitigation. Its drop/close semantics must settle tickets even before runner activation.
- Provider construction can execute auth scripts and must not run on the UI thread. Already-started subprocess or detached prompt effects may finish after cancellation; results cannot commit or execute stale work.
- Source snapshot guards deliberately delay later actor-owned setters/admissions during fresh preparation. They must expire/cancel promptly and never block already-active turn lease release. Successful heavy replacement discards queued outgoing work as current replacement does; failure releases it.
- Final runtime activation must contain no remaining provider/prompt/filesystem preparation. Failed activation must not install startup/provider projections or poison storage state. Extend production fixtures to test the full failure boundary.
- Ordinary admissions remain on existing APIs; avoid making every request use two-phase approval. The new primitive must remain generic, small, and free of plan-specific types in `maki-agent`.
- The form may move to guest plugins in PR8A. Keep plan UI state in `maki-ui` and generic configuration/admission mechanisms in `maki-agent`.
- No accepted test-infrastructure gaps or unresolved product decisions. Full state-log persistence/rewind and file restoration remain separate PR6 work.
